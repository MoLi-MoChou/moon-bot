# 主动式消息：从「你问我答」到「它也会来找你」

- 日期：2026-10-29
- 版本：v1.0
- 相关：`core/src/host/schedules.ts`、`core/src/host/memory/`、`core/src/host/turns/delivery.ts`、`core/src/host/tasks-panel.ts`、`core/src/client/approval-notices.ts`；[OpenBot 借鉴计划](2026-10-28-openbot-borrowing.md) 的 3.16；[上下文与记忆](2026-10-09-context-and-memory.md)

## 为什么

现在所有对话都由用户发起。Bot 只会在两种情况下"开口"：用户说了话，或者一条预先写好的定时 prompt 到点被投递。后者是**闹钟**，不是**判断**：它不读当天发生了什么，也不知道那句话还值不值得说。

要做到「它自己发现你可能需要什么」，缺的不是一个定时器，而是中间那段——**先做功课、再决定要不要打扰**。

## 术语

- **Proactive Messaging**：agent 主动发起消息。
- **Proactive Agent**：会主动行动而不只回应的一类 agent。
- **Mixed-Initiative Interaction**：人和 agent 都能发起对话（HCI 的老说法）。

## 五块结构，以及我们现在的位置

| # | 这一块要做什么 | 我们已有 | 缺什么 |
|---|---|---|---|
| 1 | **触发**：定时 / 事件 | `TaskScheduler`（croner + 轮询、重启恢复、五种时间规则）；有 `schedule` 来源标记 | 第一版带一个最小事件触发器（「N 分钟无进展」hook，模板来自团队代班实战）；更复杂的事件（沙盒重建等）仍是下一版 |
| 2 | **后台准备**：先做功课再说话 | 无。定时任务直接把预设 prompt 投进去 | **整块缺**。需要一次不打扰用户的准备步骤（查数据、读当天对话、核对已发过什么） |
| 3 | **筛选与去重**：值不值得打扰 | 无 | **整块缺**，而且是关键。没有它，主动消息必然变成骚扰 |
| 4 | **偏好与节流**：静默时段、频率上限、轻量格式 | 只有审批的系统通知（且从不主动请求权限）；未读判定是 `completionUnread` | 没有静默时段、没有每日上限、没有「不用回复」的格式约定 |
| 5 | **投递**：走聊天通道 | 有：`appendMessage` 唯一写路径、SSE feed、未读、任务面板 | 需要区分"用户对话"与"主动消息"，前者永不静默、后者可静默 |

## 已定的行为

### 1. 两段式：准备与投递分开

一次主动消息先**准备**再**可能投递**。准备阶段的产物是一份候选（一句话 + 依据 + 为什么觉得你在意），投不投由筛选决定。准备失败或没有候选，用户什么都看不到——**不留"我今天检查了但没事"的噪音**。

### 2. 订阅式，不是默认开

用户为某个 Bot 开一条「主动消息」订阅，必须选：

- **什么时候**（时间规则，复用现有 `TaskScheduler` 的 selector）
- **什么话题**（自由文字：工作、日程、代码、健康……）
- **每天最多几条**（默认 1）

不开订阅就永远不会有主动消息。**不做**全局默认开启。

### 3. 什么值得打扰（筛选的判定）

候选必须**同时**满足，缺一条就丢：

1. **新**：与最近 N 天已发出或已否决的候选不重复。内容指纹只做第一道粗筛——换个说法的重复它拦不住，所以后面还要过一道语义相似度阈值。
2. **有据**：能指出依据（哪天的哪段对话、哪个文件、哪次失败），说不出依据的推测一律不发。
3. **可行动或有信息量**：要么给出下一步（"这份周报第 3 节还空着"），要么给出你尚不知道的事实（"你昨天让我记的部署改到今天了"）。**只表达关心不算**。
4. **不是你刚说过的**：如果过去的 24 小时对话里已经提过，闭口。
5. **不催**：不追问没回应的请求。上一轮主动消息没被回应时，同话题当天不再发。

### 4. 什么内容值得记（总结与记忆的判定）

这是这套东西的原料。判定标准：

- **记**：用户明确表达的目标与截止时间、做过的决定及其理由、偏好与禁忌、反复出现（≥3 次）但没解决的事、失败与原因、外部事实（路径、密钥名、账号、版本）。
- **不记**：寒暄、一次性的中间步骤、可以从代码/文件重新读到的内容、模型的自我陈述、任何密钥值本身（只记名字）。
- **拿不准就不记**，并在需要时现查。记忆膨胀比记不全更伤。

记忆写入仍走现有 `remember` 路径与 300 字/条、4000 字主记忆的上限；主动消息**不新增存储格式**，只在已有记忆上读。

筛选分两段跑：**硬规则先过滤**（去重、静默时段、每日上限、已提过），**模型只做软判断**（值不值得、可不可行动）。硬规则便宜且能挡掉大多数，模型只处理剩下的，省成本也省延迟。

### 5. 节流与格式

- **每日上限**：每个订阅默认 1 条，用户可调，硬上限 5。
- **静默时段**：默认 22:00–08:00 不发（用户本地时区）。按候选的时效分级处理：时效短的（今天下午的天气）直接丢弃，时效长的（截止日期）延迟到 08:00 投递。
- **轻量格式**：一句话 + 最多 3 行依据；不写标题、不写"我今天检查了……"。
- **一键关**：用户在对话里说「别发这类」，该订阅当天停用并询问是否永久关。
- **可追溯**：每条主动消息在任务面板留一行（就像定时回合），静默掉的候选也留一行但不算未读。
- **可识别**：主动消息在界面上带轻量角标（如「主动提醒」），与用户发起的对话分开，不用点开就知道是它自己来的。

### 6. 静默回合（借 OpenBot 3.16）

定时或订阅触发的回合，如果没产生交付物、问题或失败，**只留一行记录，不计未读、不弹通知**。用户点任务面板仍能看到它跑过。

理由：长期运行的 Bot 每天跑十几次，"每次都提醒"会让人关掉通知——真出事时反而看不到。

### 7. 预授权动作模式

前六条的主动消息只**提议**，动手仍要用户那一轮说了算。第七条是另一种模式：用户一次性写下一类动作的**规则**，规则内的行动不再逐次确认。

一条规则由三部分组成：

- **触发条件**：什么时候算命中（如「团队停工超过 10 分钟」）。
- **动作范围**：可以做什么（如「把积压的活下派给成员」）。
- **禁止事项**：明确不许做什么（如「不许合 main、不许改权限、不许花钱」）。

规则内行动不再逐次审批，但仍然：

- 走同一套审计记录（谁触发、做了什么、结果如何），可在任务面板回看；
- 遵守每日上限与静默时段（除非规则里显式写明"不分昼夜"，那也要用户当场勾）；
- 越界即停在规则外，退回「只提议」。

规则的**制定、修改、撤销都走明确对话**，不在设置里藏一个开关。撤销后立即生效，规则内已排队的动作取消。

这一条和产品红线的关系：红线禁止的是「产品默认放行」。预授权是用户在具体对话里为**具体一类动作**写的、可撤销的、带禁止清单的授权，不是全局 `approvalPolicy: never`，也不改变任何默认值。

## 不做什么

- **不做默认开启**，不做"先给它权限以后再问"。预授权规则是用户当场写下来的，不是产品替他开的。
- **不做情绪化的关心**（"你今天辛苦了"）——那是最快被关掉的一类。
- **不主动发起需要审批的动作**。主动消息可以提议，但动作仍要用户那一轮明确要求。
- **不跨 Bot 汇总你的隐私**去生成建议：订阅绑定到单个 Bot 的会话，读的也是它自己的上下文。
- **不在准备阶段调用付费能力**（web_search 等）除非该订阅明确允许，否则准备只用本地已有的记忆和对话。
- 不做更复杂的事件触发器（沙盒重建、外部 webhook）——第一版只做「N 分钟无进展」这一种。

## 分两步落地

1. **先做被动版**：用户点一下「回顾今天」，得到候选列表，一条都不主动推。用来验证准备与筛选的质量。看三个数：
   - 候选被点开或回应的比例（质量）；
   - 用户关掉订阅的比例（打扰度）；
   - 说「别发这类」的次数（筛选漏判）。
   跑两周，前两项不达标就回去改判定，不进第二步。
2. **再开主动**：第一版证明候选值得看之后，才允许它按订阅定时推。

## 实现方案 v1.0

一份方案一次建成：被动版「回顾今天」不是另一个阶段，而是同一条管线的手动触发模式（跑准备+筛选、不推送、只列候选）。「先被动后主动」只是上线验证策略（§P5 三指标门），不是两套实现。

```
[触发] → [准备 Prep 只读] → [筛选 Screen 硬规则+软判断] → [投递 Deliver]
                                                    ↘ [预授权执行]（§7 命中时）
```

### 数据

- **Subscription**：`{id, botId, schedule, topics, dailyCap(默认1,≤5), quietHours(默认22:00–08:00 本地), allowPaidPrep(false), eventHook?, preAuthRules[], enabled}`。不开订阅 = 零主动消息。
- **Candidate**：`{id, subscriptionId, text, evidence[≤3, 每行带出处], whyCare, ttl('short'|'long'), createdAt, triggerSource}`。
- **DecisionLog**：`{candidateId, decision('delivered'|'quiet'|'dropped'), reason, decidedAt}`。发出与否决都记，供 7 天去重窗口查询。
- **PreAuthRule**：`{trigger, actionScope, prohibitions, respectQuietHours(默认true), dailyCap, audit[]}`。

存储沿用现有惯例：订阅与决策日志进 SQLite（新迁移追加在 `store/schema.ts` 末尾，不改编号），**不新增文件格式**。

### 三处对代码现状的修正

1. **语义去重不能依赖 embedding。** 仓库里没有任何 embedding 服务（`grep` 全空，只有一条连接器目录文案提到 vector）。v1 的去重改为：**内容指纹 + 关键词集合的 Jaccard 相似度**（本地、零成本、无外部依赖），阈值先取 0.6。等哪天真的接了 embedding，再把这一层换掉——接口留成 `similarityOf(a, b): number`，实现可替换。**这一条是硬约束**：不做「先假定有 embedding」的写法。
2. **`appendMessage` 的 `source` 已能承载标记。** 它的类型是 `Readonly<Record<string, unknown>>`，直接放 `{proactive: true, candidateId}` 即可，**不改表结构、不加列**。
3. **定时触发的改造范围比 v1.0 写的小。** `TaskScheduler` 的 `FirePrompt` 是 `(sessionId, task) => void`，不需要"加一种触发目标"，只要让投递回调按 `task.kind === 'prep'` 决定是投预设 prompt 还是跑 Prep。触发器本身不动。

### 筛选（两段，先硬后软）

硬规则（本地、任一命中即 drop 并记 reason）：每日上限 → 去重（7 天窗口，指纹粗筛 + 词集相似度）→ 24h 用户已提过 → 静默时段（`short` 丢弃、`long` 进延迟队列，08:00 重跑硬规则后再投）。

**实现时删掉了一条规则**：原方案有「上一条同话题 24h 无互动则当天不再发」。写测试时发现它是死代码——一个候选只要"和未回应那条是同一话题"，就已经先被去重规则拦下；离得远到能通过去重，那就是另一件该说的事。留着会读起来像一层不存在的保护。改由去重规则承担，并在测试里锁住这个顺序。

软判断（模型，从严，拿不准就 drop）：`evidence` 指不出处 → drop；给不出下一步或未知事实、只在表达关心 → drop。

### 失败与边界

Prep 抛错 → 隐身（任务面板一行）；同一订阅并发触发按 `subscriptionId` 加锁，后到 drop；Prep/Screen/Deliver 幂等（`candidateId` + DecisionLog 防重发）；上限按本地自然日清零；延迟队列跨天未投直接 drop。

### 验证

单测：相似度阈值（20 组正/负例）、静默分级、每日上限计数、24h 已提、并发去重、延迟队列重跑。集成：定时端到端、no-progress hook 端到端、预授权命中与越界两条、「别发这类」关闭链路。上线门：被动版跑两周，看候选点开/回应率、关订阅率、「别发这类」次数；前两项不达标不开主动。

### 预授权（§7，A 保守版）

命中规则 → 三约束检查（写审计 / 守每日上限与静默 / 越界判定）→ 执行 → 留痕。`respectQuietHours=false` 必须用户在制定规则时当场勾选并看到警告。越界即停，退回只提议。制定、修改、撤销只走明确对话。

### 与 v1.0 的三处实现差异

1. **相似度没有 embedding**（v1.0 已说明）：改用指纹 + 词集相似度，`similarityOf` 是可替换的接缝。
2. **删掉了「上一条未回应」规则**：它是死代码，见「已定的行为 §3」的说明。
3. **`appendMessage` 未改**：`source` 字段已是自由 Record，直接带 `{ kind: 'proactive', … }`，没有加列。

### 预授权的红线（实现时定死的两条）

- `preAuthGate` 只从**审批路径**调用，不在它之前：规则只能回答"本来就要问用户"的问题，不能扩大 Bot 能做的事。
- `coverableByRule` 用真实策略表判断，L3/L4 永远询问。`create_bot` 是 L4、`web_search` 是 L3，测试把这两条钉住。

### 尚未做的

- 设置页只暴露订阅与回顾；预授权规则的**编写界面**尚未接（后端端点已通，可经 `api/bot` 调用）。
- 延迟队列：静默时段的 `long` 候选记 `delayed`，但早上重跑尚未接。
- `memoryOf` 目前返回空：回顾只读当天对话，不读记忆条目。
